<h2 align="center">Урок 11 — Індекси, SARGability та плани виконання (вступ)</h2>

*Вступ:* Продуктивність стає зрозумілою, коли ви пов’язуєте предикати з індексами та планами. Тут — повторюваний цикл тюнінгу: виміряти, подивитись actual plan, змінити одну річ, переміряти. Паралельно — SARGability, seek vs scan та covering indexes у практичному вигляді.

**Сфера DBMS:** [CORE] SARGability + [CROSS] індекси/плани; приклади — [T-SQL] (SQL Server + інструменти).

Ми будемо ставитися до тюнінгу як до експерименту, а не як до “магії”. Починаємо з коректного запиту, знімаємо докази (actual plan + IO/Time), робимо одну контрольовану зміну — і повторно вимірюємо, щоб розуміти причину, а не вгадувати.

Ключова навичка — бачити, що ваші предикати *дозволяють* оптимізатору зробити. SARGable‑умова не “швидша сама по собі” — вона просто має таку форму, що індекс може зробити seek у потрібний діапазон замість scan + фільтрації. Так само ми прив’яжемо covering indexes до реальних симптомів на кшталт key lookup, щоб було зрозуміло, коли `INCLUDE` виправданий.

Після уроку у вас має з’явитися чеклист для майже будь‑якого повільного запиту: шлях доступу, форма предикатів, вимоги сортування/групування і те, чи відповідає індекс вашому workload.

## Мета
Навчитись мислити про продуктивність через (1) предикати, (2) індекси, (3) actual execution plan.

## Передумови
- Уроки 7–10

## Для кого цей урок
- Аналітики: чому той самий запит інколи “літає”, а інколи “повзе”.
- Розробники: структурний підхід до тюнінгу (виміряти → змінити → повторно виміряти).
- Новачки: плани без занурення у всі внутрішні деталі оптимізатора.

## Інструменти (рекомендовано)
- [T-SQL] SSMS або Azure Data Studio (інструменти SQL Server).
- [T-SQL] Увімкнути **Actual Execution Plan**.
- [T-SQL] Опційно: `SET STATISTICS IO, TIME ON;`.

## Безпечний робочий цикл
1. Коректний запит.
2. Actual plan + IO/TIME.
3. Одна зміна за раз.
4. Порівняння результатів.

## Терміни
- [CORE] **SARGable предикат**: форма умови, яка дозволяє ефективно використати індекс.
- [CROSS] **Seek vs Scan**: seek переходить до релевантних ключів; scan читає багато/всі рядки.
- [CROSS] **Covering index**: індекс містить усі потрібні колонки, щоб уникнути lookup (реалізація відрізняється між DBMS).

## Що таке індекс (простими словами)
**Що це:** додаткова структура даних, яка допомагає SQL Server швидко знаходити потрібні рядки, не переглядаючи всю таблицю.

**Навіщо:** більшість проблем продуктивності починаються з того, що “читаємо занадто багато”. Індекс дозволяє читати “менше, але точніше”.

**Переваги:**
- швидші `SELECT` з фільтрами та JOIN
- інколи допомагає з `ORDER BY`/`GROUP BY`

**Підводні камені:**
- кожен індекс треба підтримувати при `INSERT/UPDATE/DELETE` → записи стають повільнішими
- зайві/дубльовані індекси збільшують розмір БД і ускладнюють тюнінг

## Що означає SARGable
**SARGable** = умова у `WHERE`/`ON` дозволяє використати індекс максимально ефективно.

**Типова пастка:** функція над колонкою.
- Погано: `WHERE CONVERT(date, EventTime) = '2025-01-01'`
- Краще: `WHERE EventTime >= '2025-01-01' AND EventTime < '2025-01-02'`

## Примітка
Реальні виграші залежать від обсягів і розподілу даних. Лаби показують поведінку; для сильних відмінностей збільшуйте кількість рядків.

## Лаби

### Налаштування
У цій лабораторній ми створюємо невелику таблицю подій із передбачуваною формою: час, ідентифікатор користувача, тип події і payload. Уявіть, що це спрощена версія clickstream/телеметрії застосунку, де запити дуже часто фільтрують за користувачем і часом.

Кількість рядків спеціально невелика, щоб усе виконувалося швидко навіть на ноутбуці. Якщо хочете побачити різницю в часі “неозброєним оком”, збільшіть `TOP (5000)` (наприклад, до 500000) і повторіть лаби.

Найважливіша ідея тут — не сама таблиця, а відтворюваність. Тюнінг без відтворюваних даних швидко перетворюється на здогадки: ви не знаєте, чи зміна реально допомогла, чи просто “пощастило” з кешем/навантаженням.
**Сфера (лаби):** [T-SQL] синтаксис SQL Server + системні об’єкти (`sys.all_objects`).
```sql
DROP TABLE IF EXISTS dbo.Events;
GO

CREATE TABLE dbo.Events(
  EventID int IDENTITY(1,1) NOT NULL PRIMARY KEY,
  EventTime datetime2(0) NOT NULL,
  UserID int NOT NULL,
  EventType varchar(20) NOT NULL,
  Payload varchar(100) NULL
);
GO

;WITH n AS (
  SELECT TOP (5000) ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS n
  FROM sys.all_objects
)
INSERT INTO dbo.Events(EventTime, UserID, EventType, Payload)
SELECT DATEADD(second, n.n, '2025-01-01T00:00:00'),
       (n.n % 100) + 1,
       CASE WHEN n.n % 10 = 0 THEN 'purchase' ELSE 'view' END,
       'x'
FROM n;
GO
```

### Лаб 1 — Базовий запит + actual plan
Почніть із найпростішого коректного запиту і подивіться, що обирає SQL Server. Це ваша “база”: якщо ви не виміряли до змін, далі дуже легко оптимізувати не те місце.

У фактичному плані зосередьтесь на двох питаннях. Перше: чи рушій зробив **scan** таблиці, чи зміг **seek** у індекс? Друге: скільки роботи він виконав — скільки рядків/сторінок прочитав і скільки повернув. Саме ця різниця “прочитали багато — повернули мало” найчастіше пояснює повільні запити.

Якщо ви ввімкнули `SET STATISTICS IO, TIME ON;`, зафіксуйте логічні читання. У багатьох OLTP‑сценаріях вони краще корелюють з продуктивністю, ніж wall‑clock час, який сильно залежить від кешу і фону системи.
```sql
SELECT COUNT(*)
FROM dbo.Events
WHERE UserID = 42;
```
Крок: увімкніть **Actual Execution Plan** у SSMS/Azure Data Studio.

### Лаб 2 — Додайте індекс і перевірте seek
Тепер ми додаємо вузький “швидкий шлях” доступу: індекс на `UserID`. По суті, ви говорите SQL Server: “я часто запитуватиму події за користувачем; тримай ці дані так, щоб можна було швидко перейти до потрібного діапазону”.

Після створення індексу запускайте той самий запит ще раз. Якщо план зміниться на index seek, це означає, що оптимізатор побачив можливість прочитати значно менше сторінок, щоб відповісти на те саме питання.

Важлива ремарка: індекс — не магія. На маленьких таблицях scan інколи дешевший. Ваша ціль — навчитися читати план і розуміти, *чому* він змінився і що це означає на більших обсягах.
```sql
CREATE INDEX IX_Events_UserID ON dbo.Events(UserID);
GO

SELECT COUNT(*)
FROM dbo.Events
WHERE UserID = 42;
```
Очікувано: план зміниться зі scan на seek (або почне використовувати індекс).

### Лаб 3 — SARGable vs non-SARGable для datetime
Фільтрація за датою/часом — місце, де багато “очевидних” запитів стають повільними. Часто причина в тому, що запит виглядає коректним, але змушує SQL Server робити обчислення для кожного рядка і втрачає можливість ефективно використовувати індекс.

Діапазонний предикат (`>=` і `<`) — робоча конячка для datetime: він залишає колонку “як є” і дозволяє індексу працювати. До того ж він безпечніший за `BETWEEN` для datetime, бо верхня межа ексклюзивна і допомагає уникнути “off-by-one” з дробовими секундами.

Натомість `CONVERT(date, EventTime)` застосовує функцію до колонки. Логіка може бути правильною, але часто це означає: по індексу на `EventTime` вже не можна зробити seek, треба порахувати `CONVERT` для багатьох рядків і відфільтрувати.
SARGable:
```sql
SELECT COUNT(*)
FROM dbo.Events
WHERE EventTime >= '2025-01-01T00:10:00'
  AND EventTime <  '2025-01-01T00:20:00';
```
Non-SARGable:
```sql
SELECT COUNT(*)
FROM dbo.Events
WHERE CONVERT(date, EventTime) = '2025-01-01';
```

### Лаб 4 — Складений індекс і порядок ключів
Одноколонкові індекси — хороший старт, але реальні запити рідко фільтрують лише по одному полю. Тут ми створюємо складений індекс `(UserID, EventTime)` під дуже типовий сценарій: “для конкретного користувача покажи останні події”.

Порядок ключів у складеному індексі має значення. Коли перший ключ — `UserID`, SQL Server може спочатку звузитися до одного користувача, а далі проходити значення `EventTime` уже в правильному порядку. Якщо поміняти порядок на `(EventTime, UserID)`, виграють інші запити, але цей може стати менш оптимальним.

Зверніть увагу, як `ORDER BY EventTime DESC` узгоджується з другим ключем індексу. Саме тут індекси починають “розмовляти” з вашим запитом: predicate визначає фільтр, а ORDER BY — вимогу до впорядкування.
```sql
CREATE INDEX IX_Events_UserID_EventTime ON dbo.Events(UserID, EventTime);
GO

SELECT TOP (20) EventID, EventTime, EventType
FROM dbo.Events
WHERE UserID = 42
ORDER BY EventTime DESC;
```

### Лаб 5 — Покриття через INCLUDE
Навіть якщо ви отримали хороший seek, SQL Server може робити додаткову роботу, щоб дістати колонки, яких немає в індексі. Це часто виглядає як **key lookup**: спочатку індекс знаходить ключі потрібних рядків, а потім рушій повертається до базової таблиці (або clustered index), щоб прочитати решту колонок.

`INCLUDE` дозволяє зробити індекс “покривним”: ключі навігації лишаються `(UserID, EventTime)`, але поряд з ними зберігаються `EventType` і `Payload`. Для цього запиту це може прибрати lookup і зменшити випадкові читання.

Компроміс — розмір і підтримка. Покривні індекси — потужні, але кожна включена колонка збільшує індекс і може сповільнювати записи. У практиці “покривають” лише те, що реально потрібно для вашого навантаження.
```sql
CREATE INDEX IX_Events_UserID_EventTime_Incl
ON dbo.Events(UserID, EventTime)
INCLUDE (EventType, Payload);
GO

SELECT TOP (20) EventTime, EventType, Payload
FROM dbo.Events
WHERE UserID = 42
ORDER BY EventTime DESC;
```

### Лаб 6 — Пастка implicit conversion (концепт)
Implicit conversion — підступна проблема продуктивності, бо запит і далі “працює” і повертає коректні результати. Але оптимізатор може бути змушений у плані робити scan і конвертації замість seek і простих порівнянь.

Ментальна модель проста: для порівняння SQL Server має обрати один тип даних. Якщо він вирішить конвертувати значення колонки, ви фактично застосовуєте функцію до колонки — і часто втрачаєте SARGability. Якщо ж ви конвертуєте літерал/параметр до типу колонки, колонка може лишитися “seekable”.

У реальних системах це часто трапляється через параметри неправильного типу (наприклад, `nvarchar` параметр порівнюють з `int` колонкою). Лікування зазвичай просте: правильні типи параметрів і уникання порівнянь різних типів у предикатах.
Правило: порівнюйте значення у правильному типі.

## Підсумок
Тюнінг стає значно менш містичним, якщо ставитися до нього як до експерименту: є коректний запит, є вимірювання (план + IO/Time), і є одна зміна за раз.

Два найбільші важелі, які ви потренували тут: (1) форма предикатів, що дозволяє SQL Server використовувати індекси, і (2) дизайн індексів, який відповідає тому, як запит фільтрує та сортує. Це саме ті важелі, які найчастіше працюють у production.

І головне правило: не оптимізуйте “в повітрі”. Вимірюйте на репрезентативних даних, фіксуйте причину змін, і тримайте індекси настільки маленькими, наскільки дозволяє ваш workload.

*Висновок:* Починайте з коректного запиту й оптимізуйте доказами. Пишіть seekable предикати, будуйте індекси під filter+order і використовуйте actual plan як зворотний зв’язок, а не здогадки.
