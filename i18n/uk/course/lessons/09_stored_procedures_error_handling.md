<h2 align="center">Урок 9 — Збережені процедури та обробка помилок</h2>

*Вступ:* Процедура — це контракт: або все успішно комітиться, або нічого не змінюється, а помилки не лишають сесію “поламаною”. Ви відпрацюєте TRY/CATCH + THROW + XACT_STATE(), додасте простий аудит і навчитеся робити поведінку коду прогнозованою під збої у проді.

**Сфера DBMS:** [CROSS] “контракт” процедур + [T-SQL] шаблон обробки помилок (`TRY...CATCH`, `THROW`, `XACT_STATE()`).

Сенс не в тому, щоб “вивчити синтаксис”, а в тому, щоб стандартизувати поведінку. Коли кожна процедура має однакову форму обробки помилок, застосунок отримує передбачуваний результат (commit або rollback), логування стає змістовним, а “дивні напівзаписи” перестають виникати.

Ви потренуєтеся писати багатокрокову роботу як одну одиницю, щоб межі транзакції відповідали межі бізнес‑операції. І окремо — спостережуваність як частина коректності: невеликий аудит, записаний у правильний момент, перетворює збій з гадання на відтворюваний факт.

Після уроку ви маєте швидко відповідати на питання: який контракт успіху? що відбувається при помилці? чи операція безпечна для retry? і чи виклик завжди виходить з “чистим” станом.

## Мета
Писати production‑код у БД: передбачуваний, безпечний при помилках і зручний для супроводу.

## Передумови
- Транзакції (Урок 8)

## Для кого цей урок
- Якщо ви пишете ad‑hoc запити: як упакувати роботу в надійний “API бази даних”.
- Якщо ви backend-розробник: безпечні шаблони, що добре поєднуються з обробкою помилок у застосунку.
- Якщо підтримуєте legacy БД: що варто стандартизувати в першу чергу (помилки, транзакції, аудит).

## Як виглядає “професійний” код у БД
- Передбачуваний: або успіх повністю, або змін немає.
- Спостережуваний: можна відтворити “що сталося” (аудит/лог).
- Безпечний при помилках: помилки не “ковтаються”, транзакція не лишається в брудному стані.

## Що таке stored procedure (простими словами)
**Що це:** іменована програма, збережена в SQL Server, яку ви виконуєте з параметрами.

**Навіщо:** це “API бази даних”: застосунок викликає `EXEC dbo.usp_DoThing @Id=...` замість того, щоб щоразу надсилати довгі SQL-рядки.

**Переваги:**
- одна точка правди для логіки
- безпека: можна дати `EXECUTE`, не даючи прямого доступу до таблиць
- зручність супроводу

**Підводні камені:**
- процедура сама по собі не гарантує швидкість; потрібні правильні запити й індекси
- надлишок процедур для дрібниць може ускладнити систему
- динамічний SQL усередині процедур потребує акуратної параметризації

## Як працювати з цим уроком
1. Запустіть setup.
2. Виконайте кожен лаб і перевірте очікувану поведінку.
3. Навмисно зламайте сценарій (not found / constraint violation) і переконайтесь, що аудит не зіпсований.

## Навіщо збережені процедури
- стабільний API для застосунку
- параметризація зменшує ризик SQL injection
- права можна видавати на рівні процедури

## Обробка помилок (SQL Server)
Ключові інструменти:
- `TRY...CATCH`
- `THROW` (рекомендовано для нового коду)
- `XACT_STATE()` — щоб зрозуміти, чи можна commit/rollback

## Патерн: безпечний шаблон транзакції
```sql
CREATE OR ALTER PROCEDURE dbo.usp_DoWork
  @SomeId int
AS
BEGIN
  SET NOCOUNT ON;

  BEGIN TRY
    BEGIN TRAN;

    -- Робота тут

    COMMIT;
  END TRY
  BEGIN CATCH
    IF XACT_STATE() <> 0
      ROLLBACK;

    THROW;
  END CATCH
END;
GO
```

## Лаби

### Налаштування
Мета цього setup — створити маленьке, контрольоване середовище, де видно і “бізнес‑стан”, і “операційний стан”. Таблиця `Products` — це ваші дані, а `AuditLog` — ваша здатність потім пояснити, що саме сталося.

Зверніть увагу на check constraint для `Price`. Обмеження — це не просто “валідація”; це частина історії про помилки. Хороша процедура має передбачувано поводитися тоді, коли база відмовляється приймати некоректні дані.

Один стартовий продукт тут не випадково. Він робить happy path і not‑found path максимально однозначними — саме так і потрібно, коли ви вчитеся або стандартизуєте патерни в команді.
```sql
DROP TABLE IF EXISTS dbo.AuditLog;
DROP TABLE IF EXISTS dbo.Products;
GO

CREATE TABLE dbo.Products(
  ProductID int NOT NULL PRIMARY KEY,
  ProductName nvarchar(50) NOT NULL,
  Price decimal(10,2) NOT NULL,
  CONSTRAINT CK_Products_Price CHECK (Price >= 0)
);

CREATE TABLE dbo.AuditLog(
  AuditID int IDENTITY(1,1) NOT NULL PRIMARY KEY,
  EventTime datetime2(0) NOT NULL DEFAULT SYSUTCDATETIME(),
  Event nvarchar(200) NOT NULL
);
GO

INSERT INTO dbo.Products(ProductID, ProductName, Price)
VALUES (1, N'Keyboard', 50.00);
GO
```

### Лаб 1 — Процедура, що оновлює ціну й пише аудит
У цій лабі ми будуємо процедуру, яка одночасно має виконати три вимоги: (1) змінити дані, (2) записати аудит, (3) залишатися коректною, якщо щось піде не так. Саме така комбінація і відрізняє “продакшн‑код” від разового ad‑hoc.

Зверніть увагу на порядок дій. Спочатку `UPDATE`, потім перевірка `@@ROWCOUNT`, і лише після цього — запис у `AuditLog`. Це принципово: ви не хочете мати аудит, який стверджує “оновили”, якщо насправді рядка не було.

Так само важливий шлях помилки. Ми робимо rollback, якщо транзакція ще жива, і потім перекидаємо помилку далі через `THROW`. Процедура не “ховає” проблему, але гарантує чистий стан у БД і дає виклику можливість реагувати.
```sql
CREATE OR ALTER PROCEDURE dbo.usp_UpdatePrice
  @ProductID int,
  @NewPrice decimal(10,2)
AS
BEGIN
  SET NOCOUNT ON;

  BEGIN TRY
    BEGIN TRAN;

    UPDATE dbo.Products
    SET Price = @NewPrice
    WHERE ProductID = @ProductID;

    IF @@ROWCOUNT = 0
      THROW 50001, 'Product not found', 1;

    INSERT INTO dbo.AuditLog(Event)
    VALUES (CONCAT('Updated ProductID=', @ProductID, ' Price=', @NewPrice));

    COMMIT;
  END TRY
  BEGIN CATCH
    IF XACT_STATE() <> 0
      ROLLBACK;
    THROW;
  END CATCH
END;
GO
```

### Лаб 2 — Успішний сценарій
Тут ви підтверджуєте нормальну поведінку: рядок у `Products` оновлюється, і рівно один запис додається в `AuditLog`. Добра звичка — завжди перевіряти і бізнес‑стан, і операційний стан. Якщо дивитися лише на таблицю з даними, можна пропустити проблеми з аудитом; якщо дивитися лише на аудит, можна пропустити неправильні записи.

Спробуйте повторити виклик із іншою ціною і подивіться, як накопичується історія змін. У реальних системах зазвичай додають більше контексту (користувач, correlation id, джерело), але базовий принцип той самий: мати стійке пояснення змін.

Як бонус‑вправа, увімкніть actual plan і переконайтеся, що `UPDATE` працює по ключу `ProductID`. Хороший шаблон процедур і хороші індекси завжди йдуть поруч.
```sql
EXEC dbo.usp_UpdatePrice @ProductID = 1, @NewPrice = 60.00;
SELECT ProductID, ProductName, Price FROM dbo.Products;
SELECT TOP (5) AuditID, Event FROM dbo.AuditLog ORDER BY AuditID DESC;
```
Очікуваний результат (products):

| ProductID | ProductName | Price |
|---:|:---|---:|
| 1 | Keyboard | 60.00 |

Очікуваний результат (audit, найновіші зверху):

| AuditID | Event |
|---:|:---|
| 1 | Updated ProductID=1 Price=60.00 |

### Лаб 3 — “Не знайдено”
Сценарій “не знайдено” — це не рідкість, а буденність. ID застарівають, користувачі клікають двічі, повідомлення ретраяться, upstream‑системи змагаються. Якщо процедура не визначає поведінку для “рядок відсутній”, застосунки почнуть реалізовувати це кожен по‑своєму.

Тут процедура перетворює “нічого не оновили” на явну помилку з власним номером. Це робить результат очевидним для виклику. Головна гарантія — аудит залишається чистим: жодного фейкового запису “оновлено”.

У реальному коді варто стандартизувати номери й тексти помилок. Послідовність тут потім дуже допомагає з моніторингом та інцидентами.
```sql
EXEC dbo.usp_UpdatePrice @ProductID = 999, @NewPrice = 10.00;
```
Очікувано: помилка 50001; аудит не додається.

Запит для перевірки (після помилки):

```sql
SELECT COUNT(*) AS AuditRows
FROM dbo.AuditLog;
```

Очікуваний результат:

| AuditRows |
|---:|
| 1 |

### Лаб 4 — Порушення constraint
Цей сценарій про те, що база даних — остання лінія захисту. Check constraint не дозволяє негативну ціну. Ваше завдання не “обійти” це, а забезпечити, щоб процедура коректно закінчилася, коли база відмовляється приймати зміни.

Важлива деталь: помилка трапляється *всередині* транзакції. Якщо її не перехопити і не відкотити, можна лишити сесію у “поганому” транзакційному стані, і далі отримувати дивні вторинні помилки. Саме для цього і є шаблон `TRY...CATCH` + `XACT_STATE()`.

Знову перевірте аудит: запису бути не повинно, бо зміна не закомітилася. У продакшні це критично для довіри до аудиту.
```sql
EXEC dbo.usp_UpdatePrice @ProductID = 1, @NewPrice = -1.00;
```
Очікувано: помилка check constraint; транзакція відкатується; аудит не додається.

Запит для перевірки (після помилки):

```sql
SELECT COUNT(*) AS AuditRows
FROM dbo.AuditLog;
```

Очікуваний результат:

| AuditRows |
|---:|
| 1 |

### Лаб 5 — Ідея з правами (концепт)
Права — це місце, де процедури особливо корисні. Якщо роль застосунку може напряму оновлювати таблиці, безпека стає залежною від схеми і всіх запитів, які застосунок виконує. Якщо ж роль має лише `EXECUTE` на узгоджені процедури, ви створюєте контрольовані точки входу.

Принцип такий: роль може робити *дозволені операції*, а не довільні записи у таблиці. Це зменшує ризик, робить аудит осмисленішим і спрощує рев’ю змін: правил менше і вони в одному місці.

У реальних системах часто роблять роль на застосунок (або на capability), видають execute на набір процедур і забороняють прямий доступ до таблиць. Потім обов’язково тестують з не‑адмінського логіна, що межі реально працюють.
```sql
-- Приклад; потребує користувача/ролі.
-- GRANT EXECUTE ON dbo.usp_UpdatePrice TO SomeRole;
-- DENY SELECT, UPDATE ON dbo.Products TO SomeRole;
```

## Типові помилки
Більшість проблем зі “stored procedure” — не про синтаксис, а про контракт: що саме процедура гарантує при успіху і що гарантує при провалі. Помилки нижче — це різні способи зламати цей контракт.

`SET NOCOUNT ON` виглядає косметично, але інколи впливає на драйвери/ORM. “Проковтнути” помилку в CATCH — означає зробити дебаг і коректність неможливими. А аудит “занадто рано” створює історію, яка не відповідає реальності.

Коли ви стандартизуєте шаблон процедур у команді, ви фактично стандартизуєте поведінку під стресом і при збоях. Саме тому ці дрібниці — не дрібниці.
- Немає `SET NOCOUNT ON`.
- Помилки “ковтаються” у CATCH.
- Аудит пишеться до того, як гарантовано відбудеться COMMIT.

## Підсумок
- Обгортайте багатокрокові зміни у транзакцію.
- Використовуйте `TRY...CATCH` + `THROW`.
- Робіть поведінку процедури передбачуваною й аудованою.

- Документація Microsoft: [CREATE PROCEDURE (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/statements/create-procedure-transact-sql), [TRY...CATCH (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/language-elements/try-catch-transact-sql), [THROW (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/language-elements/throw-transact-sql), [XACT_STATE (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/functions/xact-state-transact-sql)

*Висновок:* Стандартизуйте шаблон і використовуйте його всюди. Коли помилки перевикидаються, а транзакції керуються однаково, процедури стають надійним API бази, а не джерелом прихованих станів.
