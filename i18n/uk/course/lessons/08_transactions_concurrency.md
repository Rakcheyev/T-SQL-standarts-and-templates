<h2 align="center">Урок 8 — Транзакції, конкурентність, блокування, дедлоки</h2>

*Вступ:* Саме конкурентність показує слабкі місця SQL: блокування, очікування локів і дедлоки з’являються лише під навантаженням. Ви відтворите ситуації в двох сесіях, зрозумієте роль локів та ізоляції й навчитеся патернам, що тримають транзакції малими та придатними до retry.

**Сфера DBMS:** [CORE] транзакції + [CROSS] конкурентність; специфіка SQL Server — [T-SQL] (RCSI/SNAPSHOT демо).

Цей урок спеціально практичний: ви відкриєте два вікна запитів і побачите, як вибір однієї сесії перетворюється на очікування в іншій. Саме так блокування перестає бути “теорією” і стає спостережуваною поведінкою, яку можна діагностувати.

Ми побудуємо просту ментальну модель: чому lock’и існують (коректність), чому вони інколи болять (контеншн), і як рівні ізоляції змінюють компроміс. Далі — інженерні патерни без магії: короткі транзакції, сталий порядок доступу до рядків, мінімум роботи під lock’ом і проєктування коду так, щоб “жертва дедлоку” могла безпечно повторити операцію.

## Мета
Зрозуміти, чому у проді виникають блокування/дедлоки, і вивчити безпечні патерни (з можливістю повтору).

## Передумови
- Базовий DML (Урок 4)

## Для кого цей урок
- Аналітики та BI: щоб розуміти, чому запит “висить” (blocking) і чому `NOLOCK` — ризикований “пластир”.
- Backend-розробники: щоб проєктувати безпечні записи та retry.
- Початківці DBA: щоб мати ментальну модель діагностики блокувань/дедлоків.

## Що потрібно (інструменти)
- Два вікна запитів (дві сесії) у SSMS або Azure Data Studio.
- Sandbox БД, де можна виконувати `CREATE TABLE`.

## Як запускати лаби, щоб не “зависнути”
1. Відкрийте **Session A** та **Session B**.
2. Виконуйте блоки саме у відповідній сесії.
3. Якщо Session B заблокована і треба зупинити: зробіть `COMMIT` або `ROLLBACK` у Session A.
4. Якщо щось пішло не так: повторіть **Налаштування**.

## Визначення
- **Транзакція**: одиниця роботи, яка або повністю успішна (`COMMIT`), або відкатується (`ROLLBACK`).
- **Blocking**: сесія A тримає lock, потрібний сесії B.
- **Deadlock**: дві (або більше) сесії взаємно чекають одна на одну; SQL Server обирає “жертву” (помилка 1205).

## Що реально відбувається (для новачків)
### Locks
**Що це:** механізм захисту коректності даних: SQL Server блокує (або версіонує) доступ, щоб транзакції не заважали одна одній.

**Навіщо:** без цього можна отримати неконсистентні читання або “перезапис” чужих змін.

**Переваги:**
- коректність
- передбачуваність транзакцій

**Підводні камені:**
- довгі транзакції → довше тримають lock → інші сесії чекають
- дедлоки можливі, якщо різні сесії торкаються рядків у різному порядку

### Рівень ізоляції (дуже просто)
**Що це:** правила, які визначають, що саме транзакція може читати, поки інші транзакції пишуть.

**Навіщо:** це компроміс між конкурентністю і консистентністю.

Порада новачку:
- Почніть із `READ COMMITTED`.
- Якщо blocking — реальна проблема в read-heavy системі, розгляньте RCSI/SNAPSHOT у sandbox.

## Рівні ізоляції (SQL Server)
- `READ COMMITTED` (за замовчуванням): не читає незакомічені дані, але може блокуватись записами.
- **RCSI** (Read Committed Snapshot): змінює `READ COMMITTED` на row versioning.
- `SNAPSHOT`: консистентний зріз на момент старту транзакції; можливі конфлікти при оновленні.
- `SERIALIZABLE`: найсильніший, може блокувати діапазони (range locks).

Примітка: RCSI і SNAPSHOT вимагають налаштування на рівні БД.

## Рекомендовані патерни
- Тримайте транзакції короткими.
- Доторкайтесь до рядків у сталому порядку.
- Плануйте повтор (retry) для дедлоків.

## Лаби (потрібно 2 сесії)
Відкрийте **Session A** і **Session B**.

### Налаштування
У цій серії лаб ми використовуємо максимально просту модель “переказу грошей”: два рахунки і баланс. Коли ви побачите блокування або дедлок, можна бути впевненими, що це не “баг” бізнес‑логіки, а чиста механіка конкурентності.

Ми навмисно тримаємо таблицю вузькою, щоб було легко уявити, *що саме* блокується. У реальних системах усе те саме відбувається на ширших таблицях і через кілька індексів — просто діагностика стає складнішою.

Запускайте цей setup щоразу, коли хочете повернутися до відомого стану. Для concurrency‑лабів повторюваність критична: достатньо однієї “забутої” відкритої транзакції, і далі все виглядатиме хаотично.
```sql
DROP TABLE IF EXISTS dbo.Accounts;
GO

CREATE TABLE dbo.Accounts(
  AccountID int NOT NULL PRIMARY KEY,
  Balance money NOT NULL
);

INSERT INTO dbo.Accounts(AccountID, Balance)
VALUES (1, 100.00), (2, 100.00);
GO
```

### Лаб 1 — Транзакція і rollback
Це базова обіцянка транзакції: група операторів виконується як одна одиниця роботи. Або *все* застосовується, або *нічого*. Якщо ви тільки починаєте, думайте про транзакцію як про режим “чернетки” для змін.

Код імітує переказ: списати з рахунку 1 і додати на рахунок 2. Між цими операціями ви можете виконати `SELECT`, щоб подивитися проміжний стан. У межах тієї ж транзакції ви бачите свої незакомічені зміни; інші сесії поводяться залежно від рівня ізоляції.

`ROLLBACK` завершує демонстрацію: обидва `UPDATE` відміняються. Це не лише навчальний трюк — саме rollback рятує продакшн, коли щось ламається посеред операції.
```sql
BEGIN TRAN;
UPDATE dbo.Accounts SET Balance = Balance - 10 WHERE AccountID = 1;
UPDATE dbo.Accounts SET Balance = Balance + 10 WHERE AccountID = 2;
ROLLBACK;
```
Очікувано: після rollback значення повертаються.

### Лаб 2 — Демонстрація блокування
Блокування найпростіше зрозуміти, якщо уявити, що рядок — це ресурс, який одна сесія може “утримувати”, поки змінює. Коли Session A оновлює рядок `AccountID = 1` і не закриває транзакцію, вона фактично каже: “цей рядок у процесі зміни; інші нехай зачекають”.

Session B намагається оновити той самий рядок. SQL Server має захистити коректність, тому змушує Session B чекати. Це не помилка — це вибір на користь безпеки даних.

Практичний висновок: “відкриті транзакції” не безкоштовні. Навіть якщо застосунок просто “чекає”, він може утримувати lock’и і блокувати інших. Вихід — тримати транзакцію короткою і комітити/ролбекати одразу після потрібних змін.
Session A:
```sql
BEGIN TRAN;
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 1;
-- Не комітьте
```

Session B (буде чекати):
```sql
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 1;
```

### Лаб 3 — Lock timeout
У продакшні чекати нескінченно зазвичай неприйнятно. Lock timeout перетворює “зависання” на передбачувану помилку, яку можна обробити: залогувати, зробити retry або показати користувачу.

`SET LOCK_TIMEOUT` діє в межах сесії. Він визначає, скільки часу *ця сесія* чекатиме на lock, після чого завершиться помилкою 1222. Для батч‑джобів і діагностичних скриптів це корисний інструмент.

Ідея ширша за саму команду: таймаути — частина стратегії надійності. У парі з ідемпотентністю та безпечними retry вони допомагають системі лишатися “живою” під навантаженням і конкурентністю.
Session B:
```sql
SET LOCK_TIMEOUT 2000;
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 1;
```
Очікувано: через ~2 секунди помилка 1222, якщо lock утримується Session A.

### Лаб 4 — Демонстрація дедлоку
Дедлок — це блокування з циклом: Session A тримає один lock і чекає інший, а Session B тримає інший lock і чекає перший. Якби ніхто не втрутився, обидві сесії чекали б нескінченно.

SQL Server розв’язує дедлок, обираючи “жертву”. Одна транзакція відкачується (помилка 1205), а інша продовжує. Саме тому дедлоки “нормальні” у конкурентних системах: це механізм виходу з патової ситуації.

`WAITFOR` тут потрібен, щоб зробити таймінг детермінованим і відтворюваним. У реальних системах такий таймінг створює навантаження і планувальник, через що дедлоки виглядають випадковими, поки ви не навчитеся читати deadlock graph.
Session A:
```sql
SET DEADLOCK_PRIORITY LOW;
BEGIN TRAN;
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 1;
WAITFOR DELAY '00:00:05';
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 2;
COMMIT;
```

Session B (запустити, поки A чекає):
```sql
BEGIN TRAN;
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 2;
WAITFOR DELAY '00:00:05';
UPDATE dbo.Accounts SET Balance = Balance - 1 WHERE AccountID = 1;
COMMIT;
```
Очікувано: одна зі сесій отримає 1205 (deadlock victim).

### Лаб 5 — Контур retry
Коли ви приймаєте, що дедлоки можливі, головне питання стає інженерним: “як безпечно відновитися?”. Стандартна відповідь — retry з невеликою паузою (backoff). Пауза важлива: вона зменшує шанс, що ті ж самі дві транзакції знову зіткнуться одразу.

Retry працює лише тоді, коли операція безпечна для повтору. Саме тому варто проєктувати записи ідемпотентно: якщо один і той самий логічний запит випадково виконається двічі, він не повинен “подвоїти” ефект.

Багато команд роблять retry в застосунку: там простіше керувати логуванням, backoff‑стратегією та відміною (cancellation). Але принцип той самий і в T‑SQL: тримайте транзакцію маленькою, ловіть 1205, чекайте і повторюйте.
- спробувати транзакцію
- якщо 1205, зачекати і повторити

## Типові помилки
Більшість concurrency‑проблем у продакшні — наслідок наших же рішень: транзакції тримаються відкритими довше, ніж потрібно, а різні частини коду торкаються одних і тих самих таблиць у різному порядку. Тоді рушій змушений блокувати, а при достатньому перекритті — може виникнути дедлок.

Якщо запам’ятати лише одне правило: робіть максимум підготовчої роботи *поза* транзакцією, і мінімум роботи *всередині* транзакції. Спочатку перевірки й підготовка, потім коротка транзакція: торкнулися рядків → `COMMIT`.

І нарешті, будьте обережні з “швидкими фіксами”. `NOLOCK` може прибрати очікування, але ціною коректності читання. Використовуйте його лише тоді, коли бізнес свідомо приймає неконсистентні результати — а не тому, що “так швидше”.
- Великі транзакції з багатьма не пов’язаними діями.
- “Лікування” блокувань через `NOLOCK` (може давати некоректні результати).

Практичне попередження:
- `NOLOCK` не є “просто швидше”. Це зміна гарантій коректності.

## Підсумок
- Блокування і дедлоки — це механіка конкурентності.
- Потрібно проєктувати транзакції й індекси так, щоб роботи було мінімум.

- Документація Microsoft: [SQL Server transaction locking and row versioning guide](https://learn.microsoft.com/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide), [SET TRANSACTION ISOLATION LEVEL (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/statements/set-transaction-isolation-level-transact-sql)

*Висновок:* Блокування й дедлоки — нормальна механіка. Тримайте транзакції короткими, торкайтесь рядків в одному порядку та використовуйте безпечний retry — і система лишається коректною під тиском.
