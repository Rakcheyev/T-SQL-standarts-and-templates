<h2 align="center">Урок 10 — Views, UDF, TVF: що і коли застосовувати</h2>

*Вступ:* Повторне використання в SQL має ціну: як саме ви “пакуєте” логіку, так і впливаєте на те, що бачить оптимізатор. Порівняємо view, scalar UDF, inline TVF та multi‑statement TVF з точки зору прозорості, оцінок і планів, щоб обирати абстракцію без сюрпризів.

**Сфера DBMS:** [CROSS] поняття views/functions; приклади — [T-SQL] (TVF у SQL Server + нотатки про UDF inlining).

Це урок про місце, де “гарний код” зустрічається з “гарними планами”. Два варіанти можуть бути функціонально однаковими, але рушій виконання поводиться по‑різному залежно від того, чи логіка вбудовується (inlined), чи ховається за абстракцією.

Ми розкладемо кожну конструкцію як компроміс: читабельність і повторне використання проти оптимізації й передбачуваності. Ви зрозумієте, чому inline TVF часто поводиться як параметризоване view, чому scalar UDF інколи приносить несподіванки, і чому multi‑statement TVF може давати неточні оцінки.

Мета не “заборонити інструменти”, а навчитися обирати їх усвідомлено — і підтверджувати вибір на actual plan і реальних об’ємах.

## Мета
Зрозуміти компроміси між view, scalar UDF, inline TVF та multi-statement TVF.

## Передумови
- Урок 7B (патерни віконних функцій як альтернатива)

## Для кого цей урок
- Розробники, які хочуть перевикористання логіки без неприємних сюрпризів продуктивності.
- Аналітики, які часто копіюють/вставляють однакові запити.
- Ті, хто підтримує базу з великою кількістю “хелперів”.

## Якщо ви прийшли з іншого бекграунду
- Application code: SQL‑функція схожа на звичайну функцію, але може змінити те, як оптимізатор планує запит.
- BI: view робить використання зручнішим, але не гарантує прискорення.

## Як проходити лаби
1. Створіть об’єкти (таблиці → view/функції).
2. Запустіть приклади і перевірте результати.
3. Опційно: подивіться **actual execution plan** і відмітьте, чи “інлайниться” логіка.

## Швидка карта
- [CROSS] **View**: збережене визначення `SELECT` (логічна абстракція).
- [CROSS] **Scalar UDF**: повертає одне значення на виклик.
- [T-SQL] **Inline TVF**: повертає таблицю, визначену одним `SELECT` (часто дружній до оптимізатора).
- [T-SQL] **Multi-statement TVF**: повертає таблицю, сформовану кількома операторами (можливі проблеми продуктивності).

## Що це таке (і навіщо) — для новачків
### View
**Що це:** збережений запит, який виглядає як “віртуальна таблиця”. Ви звертаєтесь до нього як до таблиці, але дані обчислюються під час виконання запиту.

**Навіщо:**
- спростити читання (не копіювати однакові JOIN/фільтри у десятках місць)
- зафіксувати “канонічну” бізнес-логіку для читання
- обмежити доступ (дати доступ до view, а не до сирих таблиць)

**Переваги:**
- менше дублювання, більше консистентності
- легше підтримувати запити в команді

**Підводні камені:**
- звичайне view не є кешем результатів; швидкість залежить від плану
- “універсальні” view з багатьма JOIN можуть бути важкими

### Scalar UDF
**Що це:** функція, що повертає одне значення.

**Навіщо:** винести повторювані обчислення (форматування/невелика бізнес-логіка).

**Переваги:**
- зручно читати код
- логіка в одному місці

**Підводні камені (важливо):**
- часто уповільнює запити на великих об’ємах, бо викликається для багатьох рядків
- може “ховати” логіку від оптимізатора (особливо на старих версіях)
- якщо всередині UDF є звернення до таблиць, це ще більше ускладнює план

### Inline TVF vs Multi-statement TVF
**Inline TVF:** повертає таблицю одним `SELECT`; зазвичай оптимізується добре (схоже на підстановку запиту).

**Multi-statement TVF:** формує табличний результат кількома операторами; інколи погано оцінює кількість рядків → гірші плани.

Примітка: SQL Server 2019+ може інлайнити деякі scalar UDF (Scalar UDF Inlining), але не всі.

## Лаби

### Налаштування
Перш ніж порівнювати конструкції, нам потрібна маленька предметна область, у якій компроміси видно неозброєним оком. Інвойси і позиції інвойсів для цього ідеальні: тут природно виникають агрегації (підсумки) і повторювані обчислення (сума по рядку).

Схема навмисно мінімальна. Наша мета — не змоделювати бухгалтерію, а створити дані, які дозволять ставити реалістичні питання: “покажи підсумок інвойсів”, “підсумки по одному клієнту”, “порахуйте повторюваний вираз”.

Під час лаб тримайте в голові правило: ви вчите не лише синтаксис, а й те, яку “форму” ви даєте оптимізатору. View та inline TVF зазвичай зберігають прозору форму запиту; scalar UDF та MSTVF можуть сховати частину логіки.
```sql
DROP TABLE IF EXISTS dbo.LineItems;
DROP TABLE IF EXISTS dbo.Invoices;
GO

CREATE TABLE dbo.Invoices(
  InvoiceID int NOT NULL PRIMARY KEY,
  CustomerID int NOT NULL,
  InvoiceDate date NOT NULL
);

CREATE TABLE dbo.LineItems(
  InvoiceID int NOT NULL,
  LineNo int NOT NULL,
  Qty int NOT NULL,
  UnitPrice decimal(10,2) NOT NULL,
  CONSTRAINT PK_LineItems PRIMARY KEY (InvoiceID, LineNo)
);
GO

INSERT INTO dbo.Invoices(InvoiceID, CustomerID, InvoiceDate)
VALUES (1, 10, '2025-01-01'), (2, 10, '2025-01-03'), (3, 20, '2025-01-04');

INSERT INTO dbo.LineItems(InvoiceID, LineNo, Qty, UnitPrice)
VALUES (1, 1, 1, 100.00),
       (1, 2, 2, 10.00),
       (2, 1, 1, 50.00),
       (3, 1, 5, 5.00);
GO
```

### Лаб 1 — View як повторно використовуваний запит
Почнемо з найпростішої абстракції — view. View — це по суті іменований `SELECT`, а отже найбільша його цінність у тому, що він прибирає дублювання і створює спільне визначення, на яке спираються різні споживачі.

У прикладі view рахує підсумки інвойсів. Це класичний use case, бо підсумки легко “поламати”: десь забули JOIN, десь неправильно згрупували, десь не той фільтр. Коли канонічна логіка живе в одному місці, шанс розбігу визначень сильно менший.

Після створення view корисно подивитися actual plan для запиту, що читає з view. У більшості випадків ви побачите, що визначення view “розгортається” всередину запиту. Це правильна ментальна модель: view — це переписування запиту, а не збережений результат.
```sql
CREATE OR ALTER VIEW dbo.vInvoiceTotals
AS
SELECT i.InvoiceID,
       i.CustomerID,
       i.InvoiceDate,
       SUM(li.Qty * li.UnitPrice) AS InvoiceTotal
FROM dbo.Invoices AS i
JOIN dbo.LineItems AS li ON li.InvoiceID = i.InvoiceID
GROUP BY i.InvoiceID, i.CustomerID, i.InvoiceDate;
GO

SELECT * FROM dbo.vInvoiceTotals ORDER BY InvoiceID;
```
Очікувано:
- Invoice 1 → 120.00
- Invoice 2 → 50.00
- Invoice 3 → 25.00

### Лаб 2 — Scalar UDF (простий)
Scalar UDF приваблюють тим, що виглядають як охайний application‑код: ви даєте ім’я обчисленню і викликаєте його як built‑in функцію. Для дрібних повторюваних виразів це може підвищити читабельність.

Але саме тут часто виникають неприємні сюрпризи з продуктивністю. Якщо функція виконується “на кожний рядок” великого набору, set‑based запит починає поводитися ближче до RBAR.

Запустіть лабу і зробіть думковий експеримент: що буде, якщо `LineItems` матиме 10 мільйонів рядків? Синтаксис не зміниться, але ціна пер-рядкового виклику стане відчутною. Саме тому “один і той самий код” може дуже по‑різному працювати на різних обсягах.
```sql
CREATE OR ALTER FUNCTION dbo.fn_LineAmount(@Qty int, @UnitPrice decimal(10,2))
RETURNS decimal(10,2)
AS
BEGIN
  RETURN CAST(@Qty * @UnitPrice AS decimal(10,2));
END;
GO

SELECT InvoiceID, LineNo,
       dbo.fn_LineAmount(Qty, UnitPrice) AS LineAmount
FROM dbo.LineItems
ORDER BY InvoiceID, LineNo;
```

### Лаб 3 — Inline TVF (часто кращий за MSTVF)
Inline TVF найкраще думати як про параметризоване view. Він повертає таблицю, але визначений одним `SELECT`, тому оптимізатор може вбудувати цю логіку в зовнішній запит так, ніби ви просто вставили `SELECT` на місці.

Це важливо, бо залишає оптимізатору контроль: він може протискувати предикати, міняти порядок JOIN, вибирати індекси, маючи повну видимість логіки. Тобто ви отримуєте перевикористання без втрати здатності рушія “мислити” про запит.

Коли ви запускаєте цю лабу, порівняйте її з view. Різниця не у слові “функція”, а в тому, що ви можете параметризувати логіку. Inline TVF дає і повторне використання, і параметри.
```sql
CREATE OR ALTER FUNCTION dbo.itvf_InvoiceTotals(@CustomerID int)
RETURNS TABLE
AS
RETURN
  SELECT i.InvoiceID, i.InvoiceDate,
         SUM(li.Qty * li.UnitPrice) AS InvoiceTotal
  FROM dbo.Invoices AS i
  JOIN dbo.LineItems AS li ON li.InvoiceID = i.InvoiceID
  WHERE i.CustomerID = @CustomerID
  GROUP BY i.InvoiceID, i.InvoiceDate;
GO

SELECT *
FROM dbo.itvf_InvoiceTotals(10)
ORDER BY InvoiceID;
```

### Лаб 4 — Multi-statement TVF (показує форму)
Multi‑statement TVF виглядає як зручний компроміс: ви можете зібрати результат крок за кроком, додати умовну логіку, а потім повернути табличний результат. Це природно, якщо ви мислите процедурно.

Прихована ціна в тому, що оптимізатор часто має менше інформації про кардинальність і розподіл рядків, бо всередині формується таблична змінна. Погана оцінка рядків легко призводить до поганих планів і “дивно повільних” запитів.

Ця лаба не каже “ніколи не використовуйте MSTVF”. Вона вчить ставитися до нього як до свідомого вибору з компромісами. Якщо MSTVF опиняється на гарячому шляху, його потрібно перевіряти планами і тестувати на реальних обсягах.
```sql
CREATE OR ALTER FUNCTION dbo.mstvf_InvoiceTotals(@CustomerID int)
RETURNS @t TABLE(
  InvoiceID int NOT NULL,
  InvoiceDate date NOT NULL,
  InvoiceTotal decimal(10,2) NOT NULL
)
AS
BEGIN
  INSERT @t(InvoiceID, InvoiceDate, InvoiceTotal)
  SELECT i.InvoiceID, i.InvoiceDate,
         SUM(li.Qty * li.UnitPrice) AS InvoiceTotal
  FROM dbo.Invoices AS i
  JOIN dbo.LineItems AS li ON li.InvoiceID = i.InvoiceID
  WHERE i.CustomerID = @CustomerID
  GROUP BY i.InvoiceID, i.InvoiceDate;

  RETURN;
END;
GO

SELECT *
FROM dbo.mstvf_InvoiceTotals(10)
ORDER BY InvoiceID;
```

### Лаб 5 — Альтернатива scalar UDF
Ця лаба показує корисну дисципліну: перш ніж загортати простий вираз у scalar UDF, спробуйте set‑based варіант “у рядку”. Багато обчислень цілком читабельні як вирази, особливо якщо ви даєте їм змістовний alias.

Сенс не в тому, що scalar UDF “поганий”, а в тому, що його реальна ціна часто недооцінюється. Якщо inline‑вираз дає ту ж читабельність, він ще й залишає оптимізатору повну видимість і часто більш передбачуваний план.

Для code review це практичне правило: за замовчуванням використовуйте inline‑вирази, а scalar UDF вводьте тоді, коли ви справді зменшуєте складність, а не просто переносите її.
```sql
SELECT InvoiceID, LineNo,
       CAST(Qty * UnitPrice AS decimal(10,2)) AS LineAmount
FROM dbo.LineItems
ORDER BY InvoiceID, LineNo;
```

## Рекомендації
Думайте про ці конструкції як про інструменти з різною “прозорістю” для оптимізатора. View та inline TVF зазвичай прозорі: оптимізатор бачить логіку і може її оптимізувати. Scalar UDF та MSTVF можуть бути непрозорими: вони ховають частину роботи і спотворюють оцінки.

Це не означає, що “непрозорі” інструменти треба заборонити. Це означає, що їх варто застосовувати там, де вигода (інкапсуляція, процедурна композиція) переважає ризики — і завжди перевіряти actual plan на репрезентативних обсягах.

Як командна практика корисно мати кілька правил (“inline TVF — за замовчуванням”, “scalar UDF — під рев’ю на великих вибірках”), бо сталі звички зазвичай ефективніші за героїзм.
- [CROSS] View — для читабельного повторного використання.
- [T-SQL] Inline TVF — для параметризованої табличної логіки.
- [T-SQL] Scalar UDF — обережно; перевіряйте плани на вашій версії SQL Server.
- [T-SQL] MSTVF — зазвичай не для “гарячих” запитів.

## Підсумок
Головна ідея проста: повторне використання в SQL Server не є “безкоштовним”. Те, як ви пакуєте логіку, змінює те, що бачить оптимізатор, а те, що він бачить, визначає, які плани він може обрати.

Якщо запам’ятати одне правило: віддавайте перевагу конструкціям, які лишають логіку видимою (view та inline TVF), і будьте свідомими, коли обираєте конструкції, що можуть приховувати роботу (scalar UDF та MSTVF). І після цього перевіряйте actual plan, а не припущення.

Далі спробуйте побудувати свій “набір цеглинок”: канонічне view для метрик, inline TVF для параметризованих фільтрів, і процедуру для багатокрокових операцій. З часом це перетворюється на ваш SQL‑API у найкращому сенсі.

- Документація Microsoft: [CREATE VIEW (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/statements/create-view-transact-sql), [CREATE FUNCTION (Transact-SQL)](https://learn.microsoft.com/sql/t-sql/statements/create-function-transact-sql)

*Висновок:* За замовчуванням обирайте прозорі конструкції (view, inline TVF), а “непрозорі” (scalar UDF, MSTVF) використовуйте свідомо. Підтверджуйте вибір actual plan на реальних об’ємах.
