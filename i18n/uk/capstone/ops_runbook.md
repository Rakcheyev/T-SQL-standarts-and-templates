# Ops runbook (capstone)

Цей runbook описує, як оперувати capstone-пайплайном “як у проді”.

## Чому це важливо (production mindset)
У проді “запустилось один раз” — не успіх. Успіх означає:
- ви можете безпечно робити retry після фейлів
- ви можете довести, що саме сталося (batch metadata + row counts)
- ви знаєте, що моніторити і як виглядає “погано”
- ви можете змінювати систему без випадкових регресій

## Послідовність запуску
1. Схема: `capstone/sql/01_schema.sql`
2. Seed дані: `capstone/sql/02_seed_data.sql`
3. Batch запуск: `capstone/sql/03_pipeline_load.sql`
4. Звіти: `capstone/sql/04_reporting_queries.sql`

**Нотатки для оператора**
- Запускайте скрипти саме в цьому порядку.
- Кожен запуск має мати унікальний `@BatchId`, якщо лише ви не робите цілеспрямований retry.
- Якщо скрипт впав посеред виконання, вважайте, що можливі часткові ефекти, і дійте за recovery workflow.

## Безпека повторного запуску (ідемпотентність)
- Batch ідентифікується через `@BatchId`.
- Метадані batch зберігаються в `etl.LoadBatch`.
- Повторний запуск того ж `@BatchId` має бути безпечним (без дублікатів).

**Safety checks, які ви маєте вміти робити**
- Перевірити переходи статусів batch (Started → Succeeded/Failed).
- Переконатися, що “publish” таблиці не ростуть при ретраях.
- Переконатися, що ключі (surrogate/natural) лишаються унікальними після rerun.

## Що моніторити
- Фейли: записи в `etl.LoadBatch` зі `Status = 'Failed'`.
- Тривалість: `StartedAt` → `EndedAt` по batch.
- Blocking: активні сесії під час batch (див. Lesson 16 для DMV запитів).
- Tempdb тиск під час трансформацій (hash joins/sorts/spills).

**Орієнтири “що добре”**
- Кожен batch завершується в `Succeeded` або `Failed` (без “завислих” станів).
- Час виконання batch стабільний у межах очікуваного діапазону.
- Ретраї не змінюють row counts у curated/published виходах.

## Recovery workflow
1. Визначте крок, який падає (staging, transform, publish).
2. Подивіться повідомлення про помилку (якщо зберігається) та row counts.
3. Виправте root cause (mismatch типів, constraint violation, відсутній індекс).
4. Запустіть той самий `@BatchId` повторно.
5. Якщо треба почати “з нуля” — створіть новий `@BatchId` і задокументуйте причину.

**Типові причини фейлів (приклади)**
- Data drift: нові значення в source ламають constraints або типи.
- Fanout: join неочікувано множить рядки на transform кроці.
- Blocking/deadlocks під час load.
- Plan regressions (змінились статистики; інша стратегія join).

## Change management
Будь-яку зміну “для продуктивності” фіксуйте доказами (IO/time + plan) у файлі `capstone/perf_tuning_notes.md`.

Додатково фіксуйте:
- який саме запит/звіт зачіпає зміна
- ризик (наприклад, parameter sensitivity, data skew)
- що будете моніторити після зміни (runtime, logical reads, row counts)

## Міні-оцінювання (самоперевірка)
1. Чим відрізняється “retry того ж `@BatchId`” від “створити новий `@BatchId`”?
2. Назвіть два способи, як пайплайн може виглядати “успішним”, але бути неправильним.
3. Які сигнали покажуть, що проблема в ресурсах vs blocking vs логічній помилці?

## Deliverables (portfolio evidence)
- Короткий запис (3–8 булетів) мінімум про один фейл, який ви обробили:
  - симптоми
  - діагностика
  - фікс
  - верифікація (row counts + batch status)
- Один приклад “safe rerun/backfill” процедури, яку ви можете виконати без здогадок.
